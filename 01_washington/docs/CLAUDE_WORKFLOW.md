# Claude Code를 활용한 데이터 분석 워크플로우

이 프로젝트는 터미널 기반 AI 코딩 에이전트인 **Claude Code**를 데이터 분석 파트너로 사용해, 데이터 확인부터 문서화까지 전체 과정을 CLI 환경에서 수행했다. 아래는 실제로 거친 과정을 순서대로 정리한 것이다.

## 1. 환경 점검부터 시작

가장 먼저 한 일은 "무엇이 준비되어 있는가"를 확인하는 것이었다. 분석에 필요한 라이브러리(pandas, numpy, scikit-learn 등) 설치 여부를 Claude Code가 직접 확인했고, 시각화(matplotlib, seaborn)와 모델링(xgboost)에 필요한 패키지가 없다는 것을 확인한 뒤 그 자리에서 설치까지 진행했다. Git/GitHub CLI 사용 가능 여부도 같은 방식으로 점검했다.

## 2. 데이터 확인 -> 정제 -> 탐색

- 원본 CSV(day.csv)의 행/열 구조, 컬럼별 dtype, 결측치를 pandas로 직접 조회
- IQR 기준으로 이상치를 탐지하고, 단순히 "이상치가 있다"에서 그치지 않고 각 이상치가 실제로 무엇 때문인지(예: 2012-10-29의 최저 대여량이 허리케인 샌디 때문임)까지 확인
- 컬럼 하나하나의 의미를 데이터 딕셔너리 형태로 정리

## 3. 시각화 방식을 사용자와 함께 선택

산점도를 그린 뒤 "다른 표현 방식을 추천해달라"는 요청에 여러 대안(회귀선, 구간별 박스플롯, hexbin, facet, 그룹별 분리)을 근거와 함께 제시하고, 사용자가 그중 하나를 선택하는 방식으로 진행했다. 이는 Claude Code가 정답을 일방적으로 정하는 대신, 데이터 특성(표본 수, 변수 유형)에 맞는 선택지를 설명하고 의사결정은 사용자가 하도록 하는 협업 패턴을 보여준다.

## 4. 모델링 중 발생한 문제를 사용자가 잡아내고, Claude Code가 원인을 설명

이 프로젝트에서 가장 중요한 지점이다.

- 1차 선형회귀에서 casual/registered를 포함해 학습시켰더니 R2가 정확히 1.0000이 나왔다. 사용자가 "이게 왜 이렇게 나왔냐"고 질문했고, `cnt = casual + registered`라는 항등식을 모델이 그대로 학습한 **데이터 누수**임을 확인하고 설명한 뒤, 해당 컬럼을 제외하고 재학습했다.
- 이후 XGBoost 튜닝 모델에서 `yr`(연도) 변수의 중요도가 34%로 1위를 차지하자, 사용자가 "이게 서비스 자체의 성장일 뿐인데 의미가 있는가? 재사용 가능한 모델을 만들려면 보정이 필요하지 않은가?"라는 방법론적 질문을 제기했다. 이 질문에 대해:
  1. 문제의 본질(이진 변수라 미래 연도로 외삽 불가)을 설명하고
  2. 실제로 `cnt`를 연도별 평균으로 나눈 "상대지수"로 detrend한 뒤 `yr`을 제외하고 재학습하는 보정 실험을 코드로 구현·실행하고
  3. 그 결과(계절/기온 계열이 82%로 재구성됨)를 바탕으로 실무에 적용 가능한 2단계 예측 파이프라인(기준선 추정 x 상대지수)까지 설계했다

이 과정은 AI가 지표 하나만 보고 "잘 됐다"고 끝내는 것이 아니라, **사람이 방법론적 의문을 제기하면 Claude Code가 그 자리에서 실험을 설계·실행해 검증**하는 실제 분석 워크플로우를 보여준다.

## 5. 모델 비교와 하이퍼파라미터 튜닝

선형회귀 -> 랜덤포레스트 -> XGBoost 순으로 모델을 늘려가며 성능을 비교했고, XGBoost에 대해 GridSearchCV로 5-fold 교차검증 기반 하이퍼파라미터 튜닝을 수행했다. 각 단계의 결과는 `outputs/model/*_result.md`로 남기고, 비교 그래프를 그리는 스크립트가 **그 md 파일들을 파싱해서** 값을 가져오도록 만들었다. 수치를 그래프 코드에 하드코딩하지 않았기 때문에, 모델을 다시 학습시키면 문서와 그래프가 자동으로 함께 갱신되고 서로 어긋날 수 없다.

## 6. 외부 리뷰를 받아 평가 설계의 결함을 발견하고 수정

프로젝트를 GitHub에 공개한 뒤 Claude Code에 "제삼자 관점에서 객관적으로 리뷰해달라"고 요청했고, 여기서 **가장 치명적인 문제**가 드러났다.

시계열 데이터인데 `train_test_split`으로 날짜를 무작위로 섞어 분할하고 있었다. 그러면 테스트 날짜의 바로 앞뒤 날이 학습셋에 들어가는데, 대여량과 날씨는 하루 사이에 거의 변하지 않으므로 모델이 "기온·계절로 수요를 추론"하는 대신 "양옆 값을 보고 가운데를 메우는" 훨씬 쉬운 문제를 풀고 있었던 것이다.

지적에 그치지 않고 분할 방식만 바꿔 실제로 측정해봤다(`src/11_split_comparison.py`):

| 분할 방식 | RMSE | R2 |
|---|---|---|
| 무작위 분할 (기존) | 655 | 0.89 |
| 시간순 분할 (수정 후) | 968 | 0.73 |
| 2011년 -> 2012년 예측 | 2,212 | -0.53 |

기존 방식이 실제 오차를 32% 낮게 보고하고 있었다. **겉보기 점수는 0.89에서 0.73으로 떨어졌지만**, 이 수정으로 얻은 것이 더 크다. 세 번째 행의 음수 R2가 앞서 4번에서 제기했던 "`yr`은 미래에 재사용 불가"라는 문제 의식이 옳았다는 **정량적 증거**가 되어, detrend 분석의 근거가 말에서 숫자로 바뀌었기 때문이다.

같은 리뷰에서 detrend 분석의 연도 평균을 전체 데이터로 계산하던 누수도 함께 발견해 학습셋 기준으로 수정했고, 문서에 서술되어 있으나 실제 코드로 존재하지 않던 어블레이션 실험 관련 문장도 삭제했다.

이어서 **같은 문제가 한 단계 안쪽에도 남아 있다는 점**을 확인했다. train/test는 시간순으로 고쳤지만, 하이퍼파라미터를 고르는 GridSearchCV의 교차검증은 여전히 기본 `KFold(shuffle=True)`로 학습 구간 내부를 섞고 있었다. 이를 `TimeSeriesSplit`으로 교체하자 동일 설정에 대한 CV 점수가 605 → 1,154로 바뀌었고(실제 test는 969), **선택되는 하이퍼파라미터 자체가 달라졌다**(`max_depth` 4→3, `learning_rate` 0.05→0.1). 채점 기준이 실전과 다르면 1등도 달라진다는 것을 수치로 확인한 셈이다.

## 7. 다중공선성 처리와 SHAP 분석

리뷰에서 지적된 마지막 항목은 `temp`(기온)와 `atemp`(체감온도)의 상관이 0.9917이라는 점이었다. 사실상 같은 변수를 둘 다 넣으면 트리가 매 분기마다 둘 중 아무거나 고르게 되고, gain 중요도가 두 변수 사이에서 임의로 쪼개진다.

이것이 이론이 아니라는 근거도 저장소 안에 있었다. 메인 모델에서는 `atemp`(0.202) > `temp`(0.119)였는데, detrend 모델에서는 `temp`(0.230) > `atemp`(0.205)로 **순위가 뒤집혀 있었다.** 따라서 `atemp`만 남기고 `temp`를 제외했고, 중복 정보였던 만큼 성능 변화는 거의 없었다(RMSE 968.39 → 968.75).

이어서 SHAP을 도입해 gain 중요도가 답하지 못하는 것을 보강했다.

- **방향**: 체감온도·계절은 양(+), 습도·풍속·악천후는 음(-)
- **형태**: 체감온도는 0.5~0.6 구간에서 정점을 찍고 그 위로는 더 늘지 않는 비선형 구조 — 선형회귀가 이 데이터에서 성능이 낮았던 이유가 곡선으로 설명됨
- **지표 간 불일치**: gain과 SHAP의 순위가 최대 3계단 차이났다. 특히 `weathersit`은 gain 3위지만 SHAP 기준 6위이고, `hum`·`windspeed`는 gain에서 과소평가되어 있었다. **어떤 중요도 지표를 쓰느냐가 해석을 바꾼다**는 것을 확인한 셈이다.

이 과정에서 `shap` 설치가 numpy를 2.x로 올려 matplotlib 3.6이 깨지는 의존성 충돌이 발생했다. 버전 조합을 numpy 2 + matplotlib 3.11로 통일해 해결하고, 전체 파이프라인을 처음부터 다시 돌려 재현을 검증한 뒤 `requirements.txt`에 그 이유를 주석으로 남겼다.

남은 한계(범주형 인코딩, `season`~`mnth` 상관, 2단계 파이프라인 미검증 등)는 숨기지 않고 REPORT의 "한계 및 남은 과제" 절에 명시했다.

이 단계가 보여주는 것은 **자기 결과물을 비판적으로 재검토하고, 불리한 결과가 나와도 그대로 반영하는 태도**다.

## 8. 지속적인 작업 기록

작업 도중 날짜 기반 워크로그(`worklog/YYYY-MM-DD.md`)를 계속 갱신해, 어느 세션에서든 상단 요약만 봐도 "직전에 어디까지 했고 다음에 뭘 해야 하는지" 파악할 수 있도록 관리했다. 이는 장기간에 걸친 분석 작업에서 컨텍스트를 잃지 않고 이어가기 위한 실무적 습관이다.

## 9. 탐색적 사후 분석: 이상치 탐지와 예측 오차의 관계

리포트 완성 이후, 사용자가 별도 세션에서 두 가지 사후 분석을 추가로 요청했다. 원본 데이터와 기존 파이프라인(`src/01~12`)은 건드리지 않는다는 조건 하에, 별도 스크립트로 진행했다.

**Isolation Forest 이상치 탐색**
- `temp`, `atemp`, `hum`, `windspeed`, `weathersit`, `cnt` 6개 변수로 Isolation Forest(contamination=5%)를 돌려 37일을 이상치로 탐지했다.
- 가장 이상 정도가 강한 상위 5일을 실제 기상 기록(외부 웹 검색)과 대조해, 4일이 허리케인 샌디·2011 핼러윈 노이스터·2011년 1월 대설 등 **실제 사건과 정확히 일치**함을 확인했다. 나머지 1일(2011-03-10, 습도=0.000)은 실제 기상(토네이도 발생 = 고습도 환경 필요)과 기록값이 모순되어 **센서/기록 오류**로 판단했다.
- z-score 기반으로 37건 각각의 직접 원인 변수를 분해한 결과 습도(38%) > 풍속(30%) > 체감온도(24%) > 대여수(8%) 순이었고, `weathersit`(범주형)은 원인이라기보다 이 변수들이 튈 때 함께 기록되는 결과 라벨에 가까움을 확인했다.
- 결과는 `outputs/anomaly/`에 저장하고, 원인 변수 분해는 dataviz 스킬 기준(팔레트 검증 포함)을 따른 시각화 아티팩트로도 제작했다.

**최우수 모델의 예측 오차 vs 이상치 비교**
- 튜닝된 XGBoost로 731일 전체를 예측해 오차 상위 10일을 뽑고, 위 이상치 37일과 대조했다. 겹치는 날은 **2012-10-29(허리케인 샌디) 단 1일**뿐이었다.
- 사용자가 "그럼 모델 성능이 부족하다는 뜻 아닌가?"라는 질문을 제기했다. 이에 대해 **이상치 탐지(입력값이 낯선가)와 예측 오차(모델이 그 패턴을 설명하는가)는 애초에 다른 것을 측정하는 개념**임을 설명하고, 근거로 다음을 제시했다:
  1. 이상치 37일 중 34일이 train 구간에 속해 애초에 오차 비교 대상이 아니었고, test 구간에 속한 나머지 3일 중에서도 실제로 크게 틀린 건 1일뿐 — 즉 궂은 날씨-수요 감소 관계는 모델이 잘 일반화했다.
  2. 오차 상위 9일(추수감사절 등)은 기상 변수로는 평범한 날 — 오차 원인이 날씨가 아니라 데이터에 없는 캘린더/이벤트 정보임을 시사한다.
  3. 유일한 교집합(2012-10-29)은 학습 기간에 유사 사례가 없던 진짜 극단 이벤트로, 어떤 모델도 못 맞추는 것이 정상이다.
- 결론적으로 이 결과를 "모델 성능 부족"이 아니라 **"입력 데이터에 없는 정보의 한계"**로 재해석했다. 이는 4번의 `yr`(연도) 외삽 불가 문제와 같은 성격의 한계로, README에 별도 절로 기록했다.

이 사후 분석은 리포트를 "완성 후 방치"하지 않고, 사용자의 후속 질문(휴일 효과·최저 대여일·오차 원인)을 계기로 프로젝트의 한계를 한 겹 더 구체화하는 과정을 보여준다.

**시간별(hour) vs 일별(day) 원본 데이터 비교**
- 사용자가 `01_washington/data/bike_sharing_hour.csv`(시간별, 17,379행)를 새로 추가하고, 기존 `day.csv`(일별, 731행)와 컬럼·기간을 비교해달라고 요청했다. **원본 데이터는 임의로 수정하지 말라**는 조건이 명시적으로 주어졌고, 이후 모든 작업에서 조회만 하고 파일을 변경하지 않았다.
- 컬럼 비교 결과: day.csv의 16개 컬럼 전부가 hour.csv에도 있고, hour.csv에는 시간대(`hr`) 컬럼 하나만 추가된 상위 호환 구조임을 확인했다. 두 파일 모두 2011-01-01~2012-12-31(동일 기간)을 다뤘다.
- 이어서 "시간별 파일의 행 수와 (일별 날짜 수 × 24)를 비교해달라"는 요청에 따라 정합성을 검증했다:
  - 기대값 731일 × 24시간 = 17,544행, 실제 17,379행 → **165시간 누락**
  - 날짜별로 관측된 시간 수를 집계해 76개 날짜에서 시간 결측이 있음을 확인하고, 결측이 가장 심한 상위 5일을 표로 제시했다.
  - 1위(2012-10-29, 23시간 누락)는 앞서 이상치 분석에서 확인한 **허리케인 샌디 상륙일**과 정확히 일치했고, 2·4·5위(2011-01-27, 01-18, 01-26)는 2011년 1월 폭설 시기와 겹쳐, 시간 결측이 무작위가 아니라 **실제 서비스 중단 이벤트와 연동된 패턴**임을 확인했다. 이는 이전 단계(이상치 탐지)의 발견을 다른 데이터(시간별 파일)로도 교차 검증한 셈이다.
  - day.csv와 hour.csv 간 날짜 자체의 불일치(한쪽에만 있는 날짜)는 없음을 확인했다.

이 단계는 새 데이터셋(런던) 작업을 시작하기 전, 기존에 있던 워싱턴 시간별 원본 데이터의 구조와 결측 패턴부터 먼저 점검한 과정이며, "원본은 건드리지 않는다"는 원칙이 이 세션 전체에서 반복적으로 지켜지고 있음을 보여준다.

**day.csv가 hour.csv의 파생 데이터인지 검증**
- "두 파일이 동일한 대상을 측정한 데이터셋으로 판단할 수 있는가?"라는 질문에, hour.csv를 날짜별로 합산한 `cnt`가 day.csv의 `cnt`와 731일 전부 정확히 일치하고 `temp` 상관도 0.9999999임을 확인해 **"예"**로 답했다. 추측이 아니라 실측으로 답했다.

**컬럼별 집계 방식 역산**
- day.csv의 각 컬럼이 hour.csv를 sum/mean/max/min/mode/first/last 중 무엇으로 집계한 결과인지 7가지 방식을 전부 계산해 대조했다. 결과: 달력형 컬럼(season 등)은 하루 내내 고정값, `temp/atemp/hum/windspeed`는 평균(731/731 일치), `casual/registered/cnt`는 합계(731/731 일치), `weathersit`만 최빈값으로도 632/731(86.5%)만 설명됨을 확인했다.
- 사용자가 weathersit에 대해 "최악 등급이 4시간 이상이면 그 값, 아니면 최빈값" 규칙을 제시했다. 이 시점에는 규칙을 **인지만 하고 데이터는 수정하지 않았다.**

**시간별→일별 변환 규칙서 작성**
- 위에서 검증한 규칙을 다른 데이터셋(런던 등)에도 재사용할 수 있도록 문서화해달라는 요청을 받았다. 작성 전 애매한 지점(결측 시간 처리 방식, 반올림 자릿수, 문서 적용 범위)을 먼저 사용자에게 질문해 확인한 뒤 진행했다:
  - 결측 시간이 많은 날도 있는 시간만으로 그대로 집계(원본 day.csv 방식과 동일)하되, 신뢰도 파악을 위한 `n_hours_observed`/`coverage_flag` 필드를 추가로 제안
  - 반올림은 원본과 동일하게 소수 6자리 유지
  - 문서 범위는 자전거 대여 데이터 전용으로 한정(런던 등에 재사용 전제)
- `01_washington/docs/HOURLY_TO_DAILY_RULES.md`로 저장했다. weathersit 보정 규칙(최악등급 4시간 이상)은 아직 731일 전체로 재검증하지 않았고, 최빈값 동률 처리 방식도 미확정임을 문서 안에 "확정이 필요한 사항"으로 명시해 남겼다 — 검증되지 않은 것을 검증된 것처럼 적지 않기 위함이다.

## 이 워크플로우가 보여주는 역량

| 단계 | Claude Code가 수행한 역할 | 사람이 수행한 역할 |
|---|---|---|
| 환경 점검 | 라이브러리 확인·설치 | 요청 및 승인 |
| 데이터 탐색 | 코드 작성·실행·요약 | 다음 확인 항목 지시 |
| 시각화 | 여러 대안 제시 및 구현 | 방식 선택 |
| 모델링 | 코드 작성·실행·지표 해석 | 결과 검증 질문 제기 (누수, 재사용성) |
| 문제 해결 | 원인 분석, 보정 실험 설계·구현 | 방법론적 문제의식 제공 |
| 자체 리뷰 | 평가 설계 결함 지적, 실측 검증, 수정 | 리뷰 요청 및 반영 결정 |
| 심화 해석 | 다중공선성 처리, SHAP 도입, 의존성 충돌 해결 | 개념 설명 요구 후 진행 결정 |
| 문서화 | 리포트·워크로그 작성 | 정리 요청 |
| 사후 분석 | 이상치 탐지, 예측 오차 분석, 두 결과의 관계 해석 | 후속 질문 제기 (성능 부족 아닌지) |

즉 이 프로젝트는 "AI가 알아서 분석했다"가 아니라, **분석가가 Claude Code라는 CLI 도구를 활용해 가설-검증-보정의 반복 사이클을 빠르게 수행한 사례**다. 특히 마지막 리뷰 단계에서 자신의 성능 수치가 과대평가되어 있었음을 스스로 찾아내 낮춰 잡은 과정은, 좋은 숫자를 만드는 것보다 **믿을 수 있는 숫자를 만드는 것**을 우선한다는 점을 보여준다.
