# 런던 시간별 → 일별 변환 계획서

`02_london/docs/PREPROCESSING_NOTES.md`에서 확정한 원칙(워싱턴과 동일한 집계 규칙, 컬럼 값은 원본 인코딩 그대로)을 실제로 적용하는 계획이다. 실행 전 계획을 먼저 문서화하고, 실행 결과는 본 문서 하단 "실행 결과"에 사후 기록한다.

## 입력 / 출력

- 입력: `02_london/data/preprocess/london_merged.csv` (원본, 수정하지 않음)
- 출력: `02_london/data/preprocess/day_london.csv` (신규 생성)

(2026-08-19: 사용자가 `data/raw/` → `data/preprocess/`로 폴더를 재배치. 이 문서와 스크립트 경로를 그에 맞춰 갱신함. 연도별 분리본은 `data/processed/`에 유지)

## 최종 컬럼 및 규칙

| 컬럼 | 종류 | 규칙 | 비고 |
|---|---|---|---|
| `dteday` | 파생 | `timestamp`의 날짜 부분 | 신규 |
| `yr` | 파생 | `timestamp`의 연도(2015/2016/2017 실제 값) | 워싱턴은 0/1(2년)로 인코딩했지만, 런던은 2015-01-04~2017-01-03로 3개 캘린더 연도에 걸쳐 있어 0/1 인덱스가 자연스럽지 않음 → **실제 연도값 그대로 사용**(전처리 최소화 원칙과 동일선상의 결정) |
| `mnth` | 파생 | `timestamp`의 월(1~12) | 신규 |
| `weekday` | 파생 | 워싱턴과 동일 인코딩(0=일요일 ~ 6=토요일)으로 산출 | 워싱턴 day.csv 731일 실측 대조로 인코딩 확인(0=Sunday) 후 동일하게 맞춤 |
| `season` | 상수형 | 하루 중 고정값 그대로 | 런던 원본 인코딩(0=spring~3=winter) 유지, 워싱턴 1~4로 리매핑 안 함 |
| `is_holiday` | 상수형 | 하루 중 고정값 그대로 | 원본 유지 |
| `is_weekend` | 상수형 | 하루 중 고정값 그대로 | 원본 유지 |
| `workingday` | 파생 | `is_weekend==0 AND is_holiday==0` → 1, 아니면 0 | 워싱턴 day.csv 731일 전체와 대조해 이 정의(주말도 휴일도 아니면 1)가 정확히 일치함을 사전 확인 |
| `weather_code` | 컨디션등급형 | 하루 24시간 중 가장 나쁜(값이 큰) 코드가 **4시간 이상**이면 그 값 채택, 아니면 **최빈값** | 원본 코드(1,2,3,4,7,10,26) 그대로, 리매핑 없음. 최빈값 동률 시 더 나쁜(값이 큰) 코드 우선(워싱턴 규칙서와 동일 원칙 적용 — 단, 이 방식으로 실제 동률이 몇 건 발생하는지는 실행 후 보고) |
| `t1`, `t2`, `hum`, `wind_speed` | 평균형 | 시간별 단순평균, **소수 2자리 반올림** | 원본 소수 정밀도가 대체로 1~2자리 수준이라 2자리가 과도한 정밀도를 피하면서 정보 손실도 없는 절충안. 워싱턴의 6자리 규칙은 정규화(0~1) 스케일 전제였기 때문에 그대로 쓰지 않음(PREPROCESSING_NOTES에 이미 명시된 결정) |
| `cnt` | 합계형 | 시간별 합계 | 원본 유지 |
| `n_hours_observed` | 파생(QA) | 그날 실제 관측된 시간 수(고유 `timestamp` 개수) | **요청사항** — 몇 시간이 기록됐는지 항상 컬럼으로 남김 |

`casual`/`registered`는 런던 원본에 없어 생성하지 않는다(PREPROCESSING_NOTES에 기 확정).

## 처리 순서

1. `london_merged.csv` 로드, `timestamp`를 datetime으로 파싱, 날짜(`dteday`) 파생
2. 날짜별 `groupby`
3. 컬럼 유형별로 위 표의 규칙 적용해 집계
4. `yr`/`mnth`/`weekday`는 `dteday`에서 파생 계산해 붙임
5. `workingday` 계산 후 붙임
6. `n_hours_observed` = 날짜별 고유 `timestamp` 개수
7. 날짜 오름차순 정렬 후 `day_london.csv`로 저장
8. 검증: 변환 후 행 수(=날짜 수와 같아야 함), `n_hours_observed < 24`인 날짜 수 집계해 보고

## 실행 결과

- 스크립트: `02_london/src/01_hourly_to_daily.py`
- 출력: `02_london/data/preprocess/day_london.csv`
- 원본 시간별 행 수: 17,414
- **변환 후 일별 행 수: 730**
- **24시간이 온전하지 않은 날 수: 34 / 730**
- `n_hours_observed` 범위: 9시간 ~ 24시간 (25시간 초과 날짜는 없음 — 서머타임 fall-back에 의한 중복 시각이 원본에 없는 것으로 보임)
- 24시간 미만 상위 5일: 2016-06-24(9시간), 2016-09-03(12시간), 2016-03-27(14시간, 서머타임 spring-forward로 추정), 2015-09-12(18시간), 2015-10-13(18시간)

**추가로 발견한 문제(계획서 작성 시 예상 못 함)**: 기간(2015-01-04~2017-01-03)은 731일이어야 하는데 실제로는 **`2016-09-02`가 원본에 단 1행도 없이 통째로 빠져 있어** 일별 결과에도 730행만 나온다. 이는 "24시간 미만" 카운트(34건)에도 포함되지 않는다 — 아예 그 날짜 자체가 결과에 행으로 존재하지 않기 때문이다. 후속 분석 시 `day_london.csv`에 2016-09-02가 없다는 점을 반드시 감안해야 한다.
