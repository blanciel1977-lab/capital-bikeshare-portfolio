# 런던 자전거 대여 분석 통합 계획서

`01_washington/`(Capital Bikeshare)에서 수행한 전처리→EDA→회귀분석→이상치탐지→리포트→워크플로우 전 과정을 참고해, 런던 데이터셋에 적용할 통합 계획을 정리한다. **이 문서는 계획이며, 아직 어떤 분석 코드도 실행하지 않았다.**

## 0. 목표

**2015년 데이터로 회귀모델을 학습해, 최적 모델로 2016년 일별 대여량(`cnt`)을 예측한다.**

| | 워싱턴 | 런던(본 계획) |
|---|---|---|
| 분할 방식 | 731일을 날짜순 80/20으로 분할 (같은 2년 구간 안에서) | **연도 단위 분할**: 2015년 전체(362일) = train, 2016년 전체(365일) = test |
| 분할 이유 | 무작위 분할 시 실제 오차를 32% 낮게 보고(검증됨) | 사용자가 "2015로 학습해 2016을 예측"을 명시적으로 요청 — train/test 간 시간적 단절이 워싱턴보다 더 명확함(연도 자체가 다름) |

- 입력(train): `02_london/data/processed/day_london_2015.csv` (362행)
- 입력(test): `02_london/data/processed/day_london_2016.csv` (365행)
- 목표변수: `cnt`

## 1. 전처리 — 이미 완료된 부분과 남은 부분

**완료됨** (`02_london/docs/DAILY_CONVERSION_PLAN.md`, `PREPROCESSING_NOTES.md` 참고):
- 시간별(`london_merged.csv`) → 일별 변환, 워싱턴과 동일한 집계 규칙(합계/평균/고정값/최악등급-최빈값) 적용
- 연도별 파일 분리(2015/2016), 2017년 3일치 제외
- `n_hours_observed` 컬럼으로 하루 관측 시간 수 보존

**이번 계획에서 새로 확인·결정한 사항** (아래 실측 근거로 확정, 워싱턴에서 배운 교훈을 처음부터 반영):

| 컬럼 | 결정 | 근거 |
|---|---|---|
| `yr` | **입력 변수에서 제외** | train(2015)에서는 상수(2015), test(2016)에서는 학습 때 본 적 없는 값(2016) — 워싱턴에서 `yr`이 미래로 외삽 불가능했던 문제(리포트 5절)가 여기서는 아예 학습조차 안 되는 형태로 더 극단적으로 나타남. 처음부터 제외해 같은 실수를 반복하지 않는다 |
| `t1`, `t2` | **`t1`(실제기온) 제외, `t2`(체감기온) 유지** | 상관계수 0.992로 사실상 동일 변수(워싱턴 temp~atemp 0.9917과 같은 패턴). 워싱턴이 체감온도를 남긴 것과 동일한 논리로 `t2` 유지 |
| `is_weekend` | **제외** | `weekday`로부터 완전히 결정되는 중복 변수(실측 확인: weekday 0·6일 때만 is_weekend=1, 나머지는 0 — 예외 없음). 워싱턴 원본 스키마에도 없던 컬럼이라 제외해도 워싱턴과 구조가 맞음 |
| `n_hours_observed` | **모델 입력 제외, QA 전용으로만 사용** | 실제 대여량과 약한 상관(0.058)뿐이라 예측에 의미 없음. 결측이 심한 날(train 18일, test 16일이 24시간 미만; test에는 `2016-09-02`가 아예 행 자체가 없음)을 사후에 걸러내거나 주석 처리하는 용도로만 사용 |

**최종 입력 변수 (9개)**: `season, mnth, weekday, is_holiday, workingday, weather_code, t2, hum, wind_speed`

**주의**: `weather_code`는 원본 코드(1,2,3,4,7,10,26)를 리매핑 없이 그대로 쓴다(`PREPROCESSING_NOTES.md`에서 이미 결정). 범주형이지만 숫자가 클수록 날씨가 나쁘다는 순서가 실측으로 확인돼 있어, 트리 모델에 순서형 숫자로 넣어도 무방하다.

## 2. 데이터 품질 점검 (신규 스크립트, 워싱턴 01번에 대응)

- `day_london_2015.csv`/`2016.csv` 결측치·자료형·기간 재확인(이미 일부 확인했으나 스크립트로 고정)
- IQR 기준 이상치 스캔 (워싱턴 방식과 동일)
- `n_hours_observed < 24`인 날짜 목록화(참고용, 제거하지 않음 — 워싱턴도 결측 많은 날을 삭제가 아니라 "사건으로 설명"하는 방향으로 다뤘음)
- `2016-09-02` 완전 결측일이 test에 없다는 사실을 명시적으로 문서화(모델이 그 날짜를 예측할 수는 있지만 실제값과 비교할 방법이 없음 → 평가지표 계산 시 자동으로 제외됨)

## 3. EDA (워싱턴 02번에 대응)

워싱턴 EDA에서 나온 패턴이 런던에도 적용되는지 확인하는 방향으로 설계한다.

| 분석 | 워싱턴에서의 발견 | 런던에서 확인할 것 |
|---|---|---|
| 기온 vs 대여량 | 비선형(고온에서 정점 후 하락) | `t2` vs `cnt` 산점도+hexbin으로 동일 패턴 재현되는지 |
| 날씨등급 vs 대여량 | 날씨 나쁠수록 급감 | `weather_code`별 boxplot (원본 코드 순서 그대로: 1→2→3→4→7→10→26) |
| 계절 x 요일 | 계절 효과가 요일 효과보다 지배적 | 동일 히트맵으로 비교 |
| 상관관계 | registered 0.946, atemp 0.631, hum -0.101 | train(2015) 기준 이미 확인: `t1` 0.638, `hum` **-0.587**(워싱턴보다 습도 영향이 훨씬 강함 — 특이점으로 리포트에 기록 예정) |

## 4. 회귀분석 (워싱턴 04~09번에 대응)

### 4.1 모델 비교

동일한 4개 모델을 같은 순서로 비교: 선형회귀 → 랜덤포레스트 → XGBoost(기본값) → XGBoost(튜닝). 각 모델은 **train(2015) 전체로 학습, test(2016) 전체로 평가**한다(중간 분할 없음 — 워싱턴의 80/20 분할과 달리 이미 연도로 나뉘어 있으므로 추가 분할 불필요).

- baseline 비교용: "train 기간 평균만 예측"했을 때의 RMSE도 함께 보고(워싱턴 리포트 4.3절과 동일하게, 모델이 실제로 기여하는지 판단하는 기준선)

### 4.2 하이퍼파라미터 튜닝

- GridSearchCV + **TimeSeriesSplit**(5-fold, `n_estimators/max_depth/learning_rate/subsample` 그리드는 워싱턴과 동일 범위로 시작)
- **CV는 train(2015) 내부에서만 수행** — test(2016)는 어떤 단계에서도 튜닝에 관여하지 않음
- 참고용으로 무작위 `KFold` CV 점수도 함께 계산해 두 방식의 격차를 비교(워싱턴에서 이 격차가 364건이었던 것처럼, 런던에서도 과대평가 정도를 수치로 남긴다)

### 4.3 변수 중요도 + SHAP

- 튜닝된 XGBoost의 gain 중요도와 SHAP을 모두 계산해 순위 차이 확인(워싱턴에서 최대 3계단 차이 났던 것과 비교)
- `t2`(체감기온) 방향성·비선형 구간을 SHAP dependence plot으로 확인

### 4.4 `yr` 관련 detrend 분석은 이번엔 불필요

워싱턴 리포트 5절의 detrend 분석(연도 효과 제거)은 애초에 `yr`을 입력에서 제외하기로 했으므로 같은 형태로는 필요 없다. 대신 **"연도 자체가 아예 다른 데이터로 예측했을 때 성능이 얼마나 떨어지는가"**가 이번 분석의 본질적 질문이므로, 4.1의 test 성능 자체가 워싱턴의 "2011→2012 예측"(리포트 4.2절 C케이스, R2 -0.53) 실험에 해당하는 실전 버전이 된다. 이 결과가 나쁘게 나오더라도(예: R2가 크게 낮음) 그 자체가 유의미한 결론이다 — 축소해서 보고하지 않는다.

## 5. 이상치 탐지 (워싱턴 사후분석에 대응, 이번엔 계획 단계부터 포함)

- Isolation Forest, `t2, hum, wind_speed, weather_code, cnt` 사용, contamination 5% (워싱턴과 동일 설정으로 시작)
- **2015+2016 전체(730행, 2016-09-02 제외)**에 대해 실행 — train/test 구분 없이 실제 이례적인 날을 찾는 목적이므로
- 상위 이상치는 실제 런던 기상 이벤트(폭설, 폭염, 테러/대형행사로 인한 통제 등)와 외부 검색으로 대조 — 워싱턴에서 허리케인 샌디를 찾아낸 것과 같은 절차
- 예측 오차 상위 10일과 이상치 목록을 대조해, 워싱턴에서 발견한 "이상치≠예측오차" 패턴이 런던에서도 재현되는지 확인

## 미결 사항 (착수 전 확인하면 좋은 것들)

- `season`(런던 0~3) vs `mnth`(1~12)의 상관 정도 — 워싱턴에서도 처리 못한 채 한계로 남긴 다중공선성(리포트 8절)과 같은 종류의 문제라 런던에서도 미리 체크만 하고 동일하게 "한계"로 남길지, 이번엔 해결할지 결정 필요
- 이상치 탐지의 contamination 비율(5%)을 런던 데이터 특성에 맞게 조정할지 여부
- 하이퍼파라미터 그리드를 워싱턴과 동일하게 시작할지, 데이터 규모(730일 vs 362일 train)를 감안해 더 좁힐지
